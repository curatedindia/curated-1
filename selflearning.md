## 1. Why Each Command, Task, and Tool Was Introduced

### 1.1 Environment & CLI Execution: `npm.cmd` vs `npm` on Windows
- **Command:** `npm.cmd <action>` instead of `npm <action>`
- **Why this was added:** On Windows systems running PowerShell, script execution policies (`RemoteSigned` or `Restricted`) frequently block `.ps1` wrapper scripts generated by Node.js installer (e.g., `npm.ps1 cannot be loaded because running scripts is disabled`). Executing `npm.cmd` directly delegates execution to the Windows Command Batch interface, bypassing PowerShell script execution restrictions cleanly and deterministically without requiring root privilege alterations.

---

### 1.2 Technology Architecture: Node.js Express Backend + React Vite Frontend
- **Why this stack was chosen:**
  1. **Strict Concurrency Control (INV-16 to INV-18):** CURATED's core risk is double-selling 1-of-1 inventory. A dedicated Node.js backend maintains an atomic in-memory/transactional queue where stock checks, hold creation, and status updates execute in one atomic turn of the event loop. Pure client-side or serverless edge solutions risk race conditions between parallel HTTP requests.
  2. **Sub-second HMR & Mobile Responsiveness:** Vite provides instant development feedback, zero bundling lag, and compact production builds optimized for Indian 4G mobile networks.
  3. **Zero Vendor Lock-in (DEL-01, DEL-08):** The application runs seamlessly on any standard VPS (DigitalOcean, AWS EC2, Linode, Render, Railway, or local development) using standard Node commands (`node server.js` and `npm run dev`).
  4. **Single Localhost Port Strategy:** The Express server can serve the API under `/api` and simultaneously serve the static Vite production build (or run with Vite proxy during development), making local hosting on `http://localhost:5000` completely frictionless.

### 1.3 Atomic Hold & Reservation System (`INV-08` through `INV-15`)
- **Task Added:** 10-Minute Checkout Reservation with Auto-Expiry Worker
- **Why this was implemented:**
  - Standard e-commerce carts do not hold inventory because stocks are large. In CURATED, almost every item has a stock count of **exactly 1**.
  - If Customer A enters checkout and opens their UPI app, Customer B must not be allowed to pay for that same item.
  - Adding a hold when checkout begins (`PENDING_PAYMENT`) reserves the item for 10 minutes (`D-01`).
  - An automated backend background timer checks for expired holds every 10 seconds. If the customer abandons the transaction, the hold automatically expires and the garment becomes available again without manual admin intervention.
  - If a customer completes payment *after* an expiry when the item was sold offline, the backend marks the order as `PAYMENT_RECEIVED_ITEM_UNAVAILABLE` and initiates an automated full refund (`INV-13`).

### 1.4 Concurrency Protection & Parallel Purchase Verification (`INV-16`, `INV-18`, `UAT-14`)
- **Task Added:** Mutex / Atomic Transaction Handler & Automated 20-Request Parallel Test Endpoint (`/api/test/parallel-purchase`)
- **Why this was implemented:**
  - Requirement `INV-18` and `UAT-14` explicitly demand proof that firing **20 parallel purchase requests** at a single-stock piece results in **exactly 1 success** and **19 sold-out rejections**, with stock remaining at 0 and never dipping below zero.
  - We implemented an atomic locking mechanism in the backend order-processing pipeline. When multiple concurrent checkout requests arrive within milliseconds, they queue through the transactional lock. The first request grabs the unit and decrements availability; the subsequent 19 requests instantly encounter `available == 0` and are rejected with `"Sorry, this piece just sold out."`

### 1.5 Offline Sale ("Mark as Sold") in 2 Taps (`INV-19` to `INV-24`)
- **Task Added:** Instant Offline Sale Modal with Hold Conflict Warning
- **Why this was implemented:**
  - Nikhil (the owner) is frequently standing in front of physical buyers while operating from a mobile phone. He cannot spend 2 minutes navigating complex forms.
  - The "Mark as Sold" button is placed directly on every product card in the Admin inventory list.
  - It opens a streamlined 2-tap bottom-sheet modal with pre-selected variant, default listing price (editable for negotiated bargaining), and payment method (Cash, UPI, Card).
  - If an online customer currently holds the piece, the system warns the admin with remaining hold seconds. If the admin confirms (`D-11`), the online hold is cancelled and any subsequent online payment is safely refunded.
  - An accidental tap can be undone via the "Void Sale" action with a mandatory reason, restoring inventory through a `Correction` ledger entry (`INV-23`).

### 1.6 Unified Immutable Inventory Ledger (`INV-02`)
- **Task Added:** Append-Only Ledger Table (`inventory_transactions`)
- **Why this was implemented:**
  - Directly overwriting `stock = stock - 1` destroys historical accountability.
  - Every single change to stock writes an immutable transaction with a timestamp, reason (`Initial Stock`, `Online Sale`, `Offline Sale`, `Restock`, `Return/Exception`, `Damaged`, `Manual Adjustment`, `Correction`), channel, and linked order.
  - The current on-hand stock is the verifiable mathematical sum of the ledger entries, making fraud, mistakes, and audit discrepancies immediately transparent.

### 1.7 Mobile-First Product Publishing Gates (`PC-12`, `ADM-07`)
- **Task Added:** Multi-Image Camera Upload + Remembered Defaults + Publishing Validator
- **Why this was implemented:**
  - Weekly drops consist of 40–50 items uploaded directly from a smartphone.
  - The admin form remembers the last-used Category, Condition, Source, and Lot Reference. Adding the next item requires only taking photos, typing the title, entering measurements, and saving.
  - Requirement `PC-12` states that incomplete drafts must never leak into the live store. The publishing validator blocks live status until: Title, Category, Condition, Price > 0, >= 1 Image, Measurements, Stock >= 1, and QC Passed = Yes are all fulfilled.

---

### 1.8 Genuine "SOLD OUT" Archive with Dynamic Social Proof (`SF-23` to `SF-29`, `BR-08`)
- **Task Added:** Algorithmic Sold Pieces Calculation & Admin Visibility Switch
- **Why this was implemented:**
  - Fake scarcity counters and fabricated "100+ bought today" badges destroy trust.
  - CURATED calculates pieces sold strictly from verified, non-voided database transactions.
  - The SOLD OUT archive has an admin master switch (`D-09`), allowing the owner to hide the section at initial launch until at least 15 verified sales have accumulated, preventing an empty or near-empty display.

---

### 1.9 No Return Policy Checkout Acknowledgement (`CK-05`, `CK-06`, `RET-01`)
- **Task Added:** Unchecked Mandatory Checkbox with Versioned Order Snapshot
- **Why this was implemented:**
  - Under Indian Consumer Protection regulations and commercial best practices, a customer must explicitly acknowledge non-returnable terms prior to payment initiation.
  - The checkout button remains disabled until the customer ticks the checkbox.
  - The order database record stores the exact policy version and timestamp of acknowledgment for audit defense in payment disputes.

- **Task Added:** Interactive Payment Gateway Modal with Razorpay-like UX & Webhook Simulation
